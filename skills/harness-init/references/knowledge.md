# Derive project knowledge and workflows

Use this analysis when selected repositories form a business system or an existing
harness needs the depth of a team handbook. Scale it to the selected activities;
small projects can keep one guide. Reuse existing authoritative facts and record
which source supports each conclusion.

## Abstract samples before applying them

Treat a reviewed repository set as evidence for reusable roles and boundaries, for example:
request producer/caller, state owner or shared writer, asynchronous consumer,
validation component and policy source. Map those roles to the target's actual
components; several roles can share a repository and one role can span repositories.
Repository count and a sample's organization are not template requirements.

Carry forward task questions, boundary decisions and evidence methods. Keep sample
repository names, business tables, signature names, resource identities, team rules
and dated online snapshots out of generic guidance. Concrete values belong only in
an explicitly synthetic fixture or a source-verified target guide. The example
workspace is a teaching fixture, not a predefined five-repository enrollment plan.

## Start with task questions

Build a task coverage table in the existing index or analysis section before
choosing more documents. Scale scenarios to the actual task/component boundaries;
a small service can use one compact guide. Do not impose a per-repository quota.

| Field | What to establish |
| --- | --- |
| User question or business result | The answer or behavior the selected work needs |
| Activity and scope | Development/test/startup/release/operations, members, region, version and unexamined external boundaries |
| Key answer | Responsible component, implementation entry, data/API boundary, configuration condition and distinguishable result |
| Source | Member-relative path and symbol/section at the reviewed baseline; label declaration, implementation, dated observation or inference |
| Document and verification entry | Answer section, native test or bounded investigation procedure |
| Gap and next action | Missing fact, why it matters and where to obtain it; leave unsupported answers pending |

Trace relevant routes, handlers, services, stores, consumers and workflows to answer
the questions. Follow request/event/timer entry points through providers and
consumers; inspect authentication/signature variants, region routing, switches and
configuration sources when they change the selected behavior. Follow data ownership,
shared writes, cache invalidation, asynchronous states, retry and idempotency bounds.
Explain how success differs from the relevant refusal or failure: HTTP response,
business code, accepted event and eventual completion are distinct observations.
For operations, give bounded queries, correlation fields, normal/abnormal meaning
and the next branch. Do not enumerate every route or table without task relevance.

Keep three scopes separate: selected members govern enrollment and writes; knowledge
scope covers interfaces needed for answers; execution scope governs tests, processes
and environment reads. An unselected worker/infrastructure repository may be a
read-only investigation within existing authorization, but cannot silently become
an analyzed member or justify end-to-end coverage. A keep-in-place document choice
does not prevent reading, citation or checking its current claims.

Treat a reference handbook as a source of questions and organization. Verify its
business claims against the target's current sources. Date historical environment
observations and show conflicting versions; never promote an old online snapshot
to a current target observation. No missing cloud login blocks independent source
analysis, but the affected environment/business result remains pending.

## Record only evidenced relationships

Populate existing `components`, `capabilities` and typed `relationships` where
source inspection establishes them. Reuse implicit components for ordinary members.
`consumes` does not imply startup/deployment order, `validated_by` does not prove a
test ran, and a capability list does not prove dependencies are deployed. Preserve
uncertain/external boundaries in the coverage table rather than declaring a partial
capability complete. Link each procedure to one authoritative fact location and use
`sources`/`provenance`; unmapped outputs retain conservative dependencies.

1. **Map services and responsibilities.** For each selected repository, identify
   entry points, owned behavior, data stores, interfaces and native commands. A
   deployment unit may differ from the repository boundary. Resolve local, CI and
   deployed runtime versions separately.
2. **Follow representative business journeys.** Start with a named user action or
   recurring symptom. Trace request/event boundaries across services, identify the
   owning data and observation points, and record the expected outcome. Investigate
   implementation where configuration cannot explain the path. Mark inferred links.
3. **Map environments.** Use workflows, infrastructure and authorized observations
   to connect environment, account/project, partition, region, resource, logs and
   artifact identity. Keep declared topology separate from live verification. A
   service name is not sufficient evidence for its deployed resource name.
4. **Extract team constraints.** Read contribution rules, release procedures, schema
   migration policy, branch conventions, incident handling and existing task systems.
   Establish where each applies. Business ownership, severity criteria, approval
   requirements and historical exceptions need a source or user input.
5. **Turn repeated work into routes.** Group tasks by their real inputs and outcomes:
   setup, service/flow investigation, bounded user-state lookup, change analysis,
   testing, release verification, schema/config changes, or collaboration. Generate
   only requested useful procedures. A fixed set of legacy Skills is not a universal
   template.
6. **Check the handoffs.** A symptom should lead to a component, source, observation,
   conclusion and next action. A proposed fix should lead to the correct checkout,
   native checks and delivery path. Specialist agents return evidence to that flow;
   they do not silently enlarge the parent task's permissions.

Useful outputs include a service index, service guides, business-flow maps,
cross-service data/API contracts, environment and toolchain guides, development/test
commands, release and operational runbooks, known pitfalls and task routing. Keep a
fact in its authoritative guide and link it from procedures.

For every selected artifact, record its purpose, inputs, sources, output path and
verification method in the generation preview or accompanying analysis. Unknown
facts remain pending with a concrete way to resolve them. The generator can validate
structure and source freshness; semantic accuracy still requires this analysis and
the requested execution checks.
