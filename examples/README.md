# Example Workspace

This synthetic workspace gives you five independently committed Git
repositories to discover, select, and analyze. The full exercise requires Node.js
24 or later for the harness helpers, Python 3.11 or later for the synthetic target
applications, and Git 2.28 or later. The target applications use the Python
standard library; they deliberately demonstrate a workspace with a different
runtime from the harness.

From the root of this repository, create the workspace in a new or empty
directory:

```sh
python3 examples/materialize.py /path/to/empty-demo
```

| Repository | Purpose |
| --- | --- |
| `api` | A loopback HTTP service with configuration and a revision endpoint |
| `client` | A command-line consumer |
| `worker` | A one-shot worker that accepts the client's greeting |
| `e2e` | A smoke test that crosses the API, client, and worker repositories |
| `product-docs` | A capability description and business acceptance criteria |

Invoke `harness-init` in the new directory. Try selecting the entire
directory, excluding one member, and choosing a different action for each
of the remaining members. The repositories have no configured remotes.
Describe the greeting scenario and select local development/testing to exercise
initialization without cloud follow-ups. To inspect a separate hypothetical cloud
plan, run `onboarding.mjs plan` with the Skill's synthetic AWS profile; that command
does not install tools or contact AWS.

## Run the smoke test

```sh
python3 /path/to/empty-demo/e2e/smoke.py
```

The smoke test starts and stops its own API instance, runs the real client,
and sends its greeting to the worker. It checks component behavior, reported
source revisions, and the worker's acceptance of the greeting. API and worker
revisions are supplied by the fixture launcher; the client reports its checkout
revision. These are declared source identities, not production artifact attestations.
Add `--json` for a bounded target, observed component artifacts and acceptance result
that a declared doctor probe can assert. This still runs the actual local scenario.

The loopback API uses its bound IP address for server metadata, so startup does not
require reverse DNS. The complete example check includes HTTP requests with reverse
DNS disabled, covering runners whose resolver cannot answer for the loopback address.

| Scenario | Command arguments | Exit status |
| --- | --- | --- |
| Expected revision and successful journey | Default | 0 |
| Healthy service on a stale revision | `--scenario stale` | 1 |
| Deployment step skipped | `--scenario skipped` | 2 |
| Correct versions, worker rejects the journey | `--scenario business-failed` | 1 |

## Export and evaluate evidence

```sh
python3 /path/to/empty-demo/e2e/smoke.py --evidence /path/to/local-record.json
node skills/harness-verify-release/scripts/evidence.mjs /path/to/local-record.json
```

The second command runs from this project's root. Add `--format markdown` for a
human-readable report with attempt history. A stale API can answer health and greeting
requests correctly, while the evaluator rejects version-bound technical acceptance.

Run the complete installation and workspace exercise in a disposable directory:

```sh
python3 examples/check.py
```

It installs all five Skills, plans and persists a local initialization profile,
discovers all five repositories, records a document review, declares a capability,
checks the workspace, and evaluates all four release scenarios using the installed
evaluator. A separate coordinator uses external member bindings, records both agent
targets and all artifact categories, then generates native configurations from the
complete synthetic spec. Artifact checks verify generated bytes, links, source
fingerprints and positive/negative hook cases. Its detached checker reports external
sources as pending unless local verification is requested. Doctor runs the selected
Python tool probe and the real greeting smoke through the e2e member's local binding,
asserting target and all three observed revisions. Those checks pass while native
agent/hook activation and hosted CI remain pending. All temporary files are
removed afterward; actual agent activation and hosted CI are not part of this exercise.

The release cases are local exercises. Every non-skipped case makes real loopback
HTTP requests and invokes the client and worker. Evidence for a hosted environment
comes from its own deployment records, running artifact, and checks.

The additional claim scenario uses a shared disposable SQLite license/outbox store.
Its API rejects a disabled claim or wrong signature contract while health remains
green; acceptance precedes the regional worker's final state change. A wrong worker
region leaves the accepted event pending, and replay after completion is idempotent.
The e2e launcher verifies these outcomes and cleanup. It models contract selection
and local asynchronous boundaries, not cryptographic signatures, a hosted broker
or production dependencies. The example harness includes task questions, a single
authoritative data-flow explanation and source references for document handoffs.

The materialized repositories are one concrete teaching topology. Abstract the
caller/producer, shared-state writer, asynchronous consumer, verifier and policy
roles when applying its lessons elsewhere. Roles need not map one-to-one to Git
repositories; repository count, fake business vocabulary and resource names are
not requirements for a target Harness.
